## 3. Discovered mismatches and their resolution

Introducing function-level verification (COMPATIBILITY_REPORT.md §2.2), and the rate-limited decode sweep added later (COMPATIBILITY_REPORT.md §2.1), uncovered and fixed several real bugs that ordinary testing alone couldn't have caught. **All of them only manifest at "boundary values ordinary test images happen not to hit,"** so extending perspective 3's and perspective 1's sweeps was what made them visible.

**→ The current list in §3.8's table is sufficient by itself. §3.1–3.10 below are the chronological investigation log behind each individual discovery.**

### 3.1 float DWT rounding error

The C reference implementation's `(int)(v + 0.5)` performs the addition in double precision, since `0.5` is a `double` literal. The Rust side was adding in single precision (`f32`), so the rounding result shifts by 1 in the rare case where a value's fractional part lands within 1 ULP of 0.5 (3 pixels out of 65536 in a 256×256 image). Found via COMPATIBILITY_REPORT.md §2.1's `-t 0` (float DWT) cases. Fixed both `round_away_from_zero` and `dwt_reverse_floating` to add via `f64`.

### 3.2 Two integer-width bugs in DPCM DC mapping

Only manifests when DC depth N=16. Found via COMPATIBILITY_REPORT.md §2.2's DPCM vectors (the sequence oscillating around the midpoint).

1. **`-(short)(...)` rounding**: C narrows the intermediate value to a 16-bit `short` before negating. When the intermediate value is exactly 32768 (when the block's raw value's top bit is set), the `short` cast wraps 32768→−32768, so the value after sign inversion becomes +32768 (the opposite sign of the −32768 Rust was computing).
2. **Unsigned wraparound in `theta = min(ShiftedDC − X_Min, X_Max − ShiftedDC)`**: `ShiftedDC`/`X_Max` are unsigned `DWORD32` in C. Once bug (1) above pushes `ShiftedDC` outside the `[X_Min, X_Max]` range (to +32768), the subtraction `X_Max − ShiftedDC` wraps around as an unsigned operation, producing a huge value instead of a negative one. C's `min()` macro then compares against this huge value, so an unintended `theta` gets chosen.

Fixed on the Rust side by using `wrapping_sub` to explicitly reproduce C's unsigned wraparound (the `neg_short`/`theta_from_prev` helpers).

### 3.3 Precision mismatch in the inverse DWT (float) — root cause identified and fixed

The C reference implementation's `inversef97f` (`lifting_97f.c`) has unsuffixed coefficient literals (`0.788486`, etc.), which are `double`, so the whole computation involving the `float` array is promoted to double precision before narrowing back to `float` at the very end. The Rust side computed entirely in single precision — a structural problem where **decoding using float DWT accumulates a small (~1e-6–1e-7) but pervasive error**. This normally didn't cross the boundary of the final pixel rounding (`(int)(v+0.5)`), so COMPATIBILITY_REPORT.md §2.1's basic cases never surfaced it, but it actually shifted a pixel by 1 at segment size 64, rate 0.1/0.75 (COMPATIBILITY_REPORT.md §2.1's rate sweep).

Changing `inverse_lifting97f`'s formulas to compute via `f64` intermediates (reproducing C's promotion) made 8 of the 10 float-DWT cases targeted by the sweep newly byte-match. **The remaining 2 (0.1, 0.75) still shifted by 1 pixel.** Isolating it to a single level and a single function call with `verify/compare_traces.py` found, in practice, cases where the C and Rust sides used identical coefficients (byte-identical f64 literals, confirmed empirically) yet the results differed by 1 ULP. This was initially, and **incorrectly**, judged to be an unresolvable residual difference stemming from gcc's and rustc's (LLVM's) floating-point rounding implementations, not an algorithm bug. However, after re-investigating in response to a later user request to "seriously resolve" it, it turned out to be **a genuine, fixable bug on the bpe-rs side**.

The same phenomenon had also been confirmed when checkerboard and noise images were added to the same sweep (quantified under §7's former item 2). The frequency varies with image content: baseline_256 (gradient) hit it in 2 of 8 rate values, checkerboard_256 in 0 of 10, and noise_256 (pseudo-random, the widest coefficient distribution) in 3 of 10. The tendency that "images with a wider, more extreme coefficient distribution are more likely to hit the 1-ULP boundary" is consistent with the true cause described below (rounding-error accumulation at the f32-addition stage).

**Two hypotheses rejected under the original misdiagnosis** (which turned out to be off-target, but kept here as a record of the investigation):

1. **`-ffp-contract=off`** (explicitly disabling FMA (fused multiply-add) contraction in the C reference implementation's C compiler): no change in the result. This build environment's gcc default target (the `x86-64` baseline) has `-mfma` disabled and can't generate hardware FMA instructions in the first place, so this correctly confirmed FMA contraction wasn't the cause.
2. **`-O0`** (fully disabling the C compiler's optimizations): this made things *worse* (34646 of 65536 pixels mismatched). The compile-time constant-folding hypothesis was also correctly rejected.

**Added level-granularity trace points to narrow it down**: added `post_idwt_level2`/`post_idwt_level1` to `compare_traces.py` (dumps right after each level's row pass in `lifting_f97_2D`/`lifting_f97_2d`, levels=3 fixed, processing column-pass then row-pass in level order 2→1→0). Running against the known-reproducing case (`baseline_256`, rate=0.1, `-t 0`, segment=64) showed `reassembled` (right before the inverse transform) matching exactly, but a divergence already present at the coarsest level (`post_idwt_level2`) (index 3, diff=-7.63e-6). This narrowed the search from "somewhere in the 3 levels" down to "somewhere within the first level."

**The true root cause**: the oversight was that C's "usual arithmetic conversions" apply **per operator, not to the whole expression**. `inversef97f`'s actual formulas take the form, for example, `0.0406894 * (x[r_idx+1] + x[r_idx-1])`, where both operands of `x[r_idx+1] + x[r_idx-1]` inside the parentheses are `float`, so **that addition itself happens in single precision (`float`) first**. That `float` sum only gets promoted to double precision once it's multiplied by the unsuffixed (`double`) coefficient `0.0406894`. bpe-rs's implementation, however, converted each addend to `f64` individually **before** the addition (`f(x[r_idx+1]) + f(x[r_idx-1])`, an addition of two values that were already `f64`). "Convert to f64 first, then add" and "add in f32, then convert to f64" aren't mathematically equivalent, since rounding error can occur at the f32-addition stage — this was the true cause of the 1-ULP difference.

**Fix**: added `fp(a: f32, b: f32) -> f64` (a helper that adds in f32 and then converts to f64) to `inverse_lifting97f` in `bpe-rs/src/wavelet/lifting97f.rs`, and switched every pairwise-addition site to go through this helper (faithfully reproducing C's per-operator type-conversion rules). Also added a regression test with hardcoded real data (a 64-element array, the actual intermediate values from decoding `baseline_256` at rate=0.1).

**Verification results**:
- Minimal reproducing case (a 64-element standard input): 13 of 64 elements mismatched before the fix → **0** after.
- Known-reproducing case (`baseline_256`, rate=0.1, `-t 0`, segment=64): `post_idwt` matches exactly, and the final output is byte-identical too.
- All 5 rate values previously excluded for `baseline_256`/`noise_256` are back to byte-identical.
- `verify/run_compat.sh --include-slow`: **178/178 PASS** with all exclusions removed.
- `verify/fuzz_compat.py --dwt-type both`: 0 mismatches across both 500 cases (seed=123) and 3000 cases (seed=999).

**Encode-side check**: also checked whether the same kind of bug exists on the encode side (the forward DWT, `forwardf97f`). The C reference implementation's `LowPassFilter`/`HighPassFilter` (the coefficients `forwardf97f` uses) are declared `const float` — unlike the inverse-transform side's `LowPassFilterInverse`/`HighPassFilterInverse` (`double const`), they're single precision from the start. So there's no room for this kind of promotion-timing difference to arise on the forward side, and no bug exists there. This resolves the encode-side concern that §7's former item 2 flagged as "to be checked in the future."

**Conclusion**: the precision mismatch in the inverse DWT (float) has been root-caused and fully fixed. The original judgment — "an unresolvable residual difference due to a compiler difference between gcc and rustc" — was wrong. It was actually a fixable implementation bug rooted in addition order (float-first vs. f64-first).

### 3.4 Additional verification of AC-side DPCM (no bug)

Following the discovery of the DC-side DPCM bug, additional verification (COMPATIBILITY_REPORT.md §2.2) was done to check whether AC-side `DPCM_ACMapper`/`DPCM_ACDeMapper` has the same kind of problem. On the AC side, `BitMaxAC`/`MappedAC` are `WORD16` (unsigned 16-bit), which C's integer-promotion rules promote to `int` (signed), so the kind of unsigned wraparound seen with the DC side's `DWORD32` (roughly unsigned 64-bit) can't happen in principle — this type-analysis prediction was actually verified by generating vectors, and **confirmed no mismatches**. This kept faith with this project's verification policy of not leaving an "it shouldn't happen" claim unmeasured.

### 3.5 Exhaustive direct-call verification of `AdjustOutPut` (no bug)

As described later in §4, no matter how much the rate and image content were expanded in the full-pipeline byte-compatibility test (perspective 1), it turned out most of `AdjustOutPut` (the rate-limited mid-decode recovery function, the single largest function at about 49% of the whole core algorithm) — specifically the in-block stopping coordinates (`X_LocationStopDecoding`/`Y_LocationStopDecoding`, 64 combinations of 8×8) — was effectively unreachable, since it depends on wherever the bitstream's remainder happens to run out.

So the same technique used for Rice/DPCM/pattern mapping — "link directly against the C reference implementation's object code and call the function standalone" — was applied to this function too (`verify/c_unit_tests/gen_adjust_output_vectors.c`). It directly constructs `StructCodingPara`/`BitPlaneBits` and directly drives all 1024 combinations of `DWTType` (integer/floating-point) × `stoppedstage` (1–4) × presence of the DC branch (2) × in-block stopping coordinates `X/Y_LocationStopDecoding` (8×8=64), cross-checking the resulting 8×8 block coefficients (both int and float, 3 blocks' worth) between C and Rust.

**Result: 1024/1024 cases, all matching.** No mismatches were found in `AdjustOutPut`/`adjust_output`, including the fine details of stopping coordinates the full-pipeline test couldn't reach.

### 3.6 Value diversification for `AdjustOutPut`'s direct calls (no bug)

§3.5's 1024 cases had complete **structural** coverage of "which DWTType × stoppedstage × X/Y coordinate is exercised," but `AdjustOutput.c`'s coverage plateaued at 97.35%, with 95 lines still unexecuted (§4). Looking into it, **almost all** of the 95 lines were one side of a sign-dependent branch pair of the form `if(coeff > 0) coeff += X; else if(coeff < 0) coeff -= X;`. The cause: `int_val`/`float_val` (values deterministically hashed from a block's (block, m, n)), which §3.5's generator uses, only ever generated a value of **the same sign** for the specific cell position corresponding to a given structural path (a stoppedstage × X/Y-coordinate combination) — even trying all 1024 structural combinations, that cell's value-sign dimension stayed fixed.

As a countermeasure, a `variant` dimension (4 values, 0–3) was introduced to `int_val`/`float_val` that applies sign inversion and phase shift, expanding the existing 1024 combinations to 1024 × 4 variants = 4096. Additionally, it turned out the `else` branch of `b_DC = min(BitPlaneStopDecoding, QuantizationFactorQ)` (the case `BitPlaneStopDecoding > QuantizationFactorQ`) was never true under the previous 2 b_DC settings, so a third b_DC setting satisfying it was added (6144 total).

**Result**: `AdjustOutput.c`'s standalone coverage (the direct-call generator alone, not combined with other tests) rose from 95.70% to 99.55%. The same `variant` logic was replicated on the Rust side in `bpe-rs/src/adjust.rs`'s tests, confirming all 6144 cases match (no mismatches).

Tracing the remaining 16 lines (8 lines × 2 sites, the integer half and the floating-point half respectively) via control-flow analysis found them to be **structurally unreachable redundant guards**: the `else` clause containing these 16 lines corresponds to the `else` side of the condition `if((m<4)&&(n<4))` (i.e. `m>=4 || n>=4`), but by the time control reaches the scope this `else` clause sits in, `m<=3 && n<=3` is already guaranteed by an outer branch (one that handles `m>3||n>3` separately, first). So `(m<4)&&(n<4)` is always true, and that `else` can never mathematically execute. Confirmed purely by reading the source code (the relationship between `AdjustOutput.c:298`'s condition and its outer `m>3||n>3` guard).

This brought `AdjustOutput.c`, combined with §4's full pipeline test, up to 97.35%→99.55% lines and 85.16%→87.15% branches, and **the remaining 16 lines are all confirmed dead code, for 100% effective coverage**.

### 3.7 Decode-side ignoring of `-f` (PixelByteOrder)

Discovered while further investigating `bpe_decoder.c`'s coverage (§4). `PixelByteOrder` isn't part of the bitstream header — in the C reference implementation it's simply a **per-call CLI setting** (defaulting to 0 at `header.c:91`, parsed from `-f` at `main.c:170`). That is, in the C reference implementation, the `-f` given at decode time determines that decode call's output byte order, independent of the value used at encode time.

However, `verify/run_compat.sh` had never once passed `-f` to the decode-side calls (it was only included in the encode side's common arguments, never passed to the 4 decode calls). Since this machine is little-endian, every existing case that didn't pass `-f` was always decoded with the decode side's default (0 = little-endian), so the "swap bytes if the requested order differs from the machine's native order" branch (`PixelByteOrder != machineendianness`) inside `ImageWrite`/`ImageWriteFloat` had never once been taken on either the C or the Rust side.

While filling in `bpe_decoder.c`'s coverage, `run_compat.sh` was fixed to also explicitly pass `-f` to the decode calls (existing cases kept defaulting to their own encode-time value, new cases deliberately specified an inverted value), and **this exposed a mismatch that had been hidden on the bpe-rs side**: 12 cases newly FAILed, including `pixels16_f1` (an existing case that both encodes and decodes with `-f 1`).

Root-cause investigation found: `bpe-rs/src/main.rs` always parsed the CLI's `-f` into a local variable, but only reflected it into `CodingPara.pixel_byte_order` on the **encode branch** — on the decode branch it was silently dropped without being assigned. `image_write`/`image_write_float`'s (`src/image_io.rs`) own swap-decision logic had been correctly ported from the C reference implementation, but since `pixel_byte_order` always stayed at the struct's default value of `0`, whatever `-f` was specified at decode time, only the "no swap needed" side was ever taken.

Fixed by adding `coding.pixel_byte_order = byte_order;` to the decode branch (the same single line as the corresponding line in the encode branch). After the fix, all cases in COMPATIBILITY_REPORT.md §2.1 PASS (including the 12 that exposed this mismatch — §2.1 had 87 cases at the time of discovery, and has since grown to the current 166 with subsequent additions for AC/DC/StagesCodingGaggles).

**Implication**: this mismatch went unnoticed all the way to case 87, because the full-pipeline test (perspective 1) had never once included a case that actually requests a non-default byte order at decode time. This is one example where coverage measurement — visualizing where perspective 1 does and doesn't exercise the C code — directly led to discovering not just untouched C code, but also **a gap in the test matrix itself** (a missing pattern that had been hiding a Rust-side bug).

### 3.9 Verifying the test suite's detection power via mutation testing

Since code coverage only sees "was this code path executed," as extra insurance backing up §7 item 13's point ("100% coverage isn't a proof for all input values"), bugs (mutations) were deliberately injected into bpe-rs's source to check whether the existing test suite actually detects them. `cargo-mutants` (v27.1.0) was introduced, targeting the 8 files where the shared-vector tests (Rice/DPCM/PatternMapping/AdjustOutPut/CodingOptions/ACDepthEncoder/DCEntropyEncoder, all marked `#[ignore]` and only run with `--include-ignored`) actually have an effect.

**Incident and recovery during the automated run**: `cargo-mutants`'s automated mode had 2 constraints. (1) When `--in-place` (a fast mode that mutates the real source directly for testing) was run in the background, the harness's background-task tracking failed to detect the actual process finishing and falsely reported "complete," while the process itself kept running undetected and left `bpe-rs`'s source files mutated. The process was found via `ps aux` and `kill`ed, and recovery was confirmed via `git status`/`git diff` showing every file matched HEAD exactly (no harm done). (2) The default scratch-copy mode (without `--in-place`) is safe, but the `#[ignore]` tests reference a relative path, `../verify/vectors/*.txt`, that doesn't resolve from the temporary copy directory, since it's a file that lives in the `bpe-c-comparison` parent repository — so a run with `--include-ignored` couldn't work at all. Because of this constraint, the automated run's results are a measurement against "only the tests that are always active."

**Automated run results**: across 8 files and 1131 mutants, 383 detected, 655 undetected, 73 unbuildable (invalid mutants), 20 timeouts. The roughly 63% undetected rate is high, but this mainly reflects a limitation of the measurement method itself: `adjust/stage3.rs`/`adjust/stage4.rs` (`AdjustOutPut`'s body, accounting for 324 of the 655 undetected) aren't covered by the always-active tests at all — they're only verified by the `adjust_output` shared-vector test (6144 combinations, §3.5, §3.6) — so the number underestimates the test suite's actual detection power.

**Manual verification for corroboration**: 5 mutants the automated run classified as "undetected" (`pattern/options.rs`, `ac/depth.rs`, `dc/entropy.rs`, `adjust/stage4.rs`, `rice/encode.rs` — each changing a single comparison or arithmetic operator in core logic) were selected, manually applied to the real bpe-rs source, and run through `cargo test -- --include-ignored` for the corresponding shared-vector tests, restoring via `git checkout` each cycle.

| File:line | Mutation | Verdict |
|---|---|---|
| `dc/entropy.rs:74` | `bit_depth_ac_5bits < quantization_factor_q` → `==` (the trigger condition for §4.3.3's extra bitplane — the exact condition where a test-harness bug was found in an earlier round) | **Detected** (`dc_entropy_shared_vectors_match_c_reference` fails) |
| `pattern/options.rs:31` | `sym_len == 1` → `!=` | **Detected** (the `coding_options` shared-vector test fails) |
| `ac/depth.rs:47` | `dpcm_ac_mapper`'s `x_max` computation, `- 1` → `+ 1` | **Detected** (both the AC DPCM and ACDepthEncoder shared-vector tests fail) |
| `adjust/stage4.rs:22` | `ii < stop_block` → `==` (a branch in `AdjustOutPut`'s body) | **Detected** (the `adjust_output` shared-vector test fails — confirming that `stage3`/`stage4`, which the automated run classified as "324 undetected," are in fact almost entirely detectable) |
| `rice/encode.rs:74` | `input_val - 4` → `input_val + 4` (bit_length=4, option[2]==0, the 2-bit remainder for inputs 4–7) | **Turned out to be an equivalent mutant** (see below) |

4 of the 5, despite being classified as "undetected" by the automated run, were reliably detected by the actual full test suite (including `--include-ignored`) — confirming the automated run's figure of 655 is an underestimate caused by the measurement tool's constraint (the relative-path resolution issue), not a weakness in the test suite itself.

**Discovering an equivalent mutant**: the one case that went undetected, `rice/encode.rs:74`, only outputs the low-order bits of the specified bit width (`bits_write` writes out `(bit >> i) & 1` for exactly that many bits), so for `input_val` in the range 4–7, `input_val - 4` (0–3) and `input_val + 4` (8–11) are completely identical in their low 2 bits (e.g. 4 → 0 or 8, both `00` in the low 2 bits). In other words, this mutation changes the output byte stream not at all — a **mathematically equivalent mutation** that no test, however constructed, could ever detect in principle — not a weakness of the test suite, but a known limitation of mutation testing (equivalent mutants occur at some rate under any classification method).

**Conclusion**: as far as manual sampling could corroborate, this project's shared-vector test suite (including `--include-ignored`) has been confirmed to have real, effective detection power against deliberately injected bugs, with a high probability of catching them. A fully automated, large-scale mutation test (mechanically running all 1131 mutants with `--include-ignored`) wasn't feasible this round, due to `cargo-mutants`'s relative-path-resolution constraint — it would be possible by separately building a mechanism that pre-generates test vectors the same way CI's `verify/run_unit_vectors.py` does, then runs `--in-place` safely and automatically, but manual-sampling corroboration was judged sufficient for this round's cost/benefit.

### 3.10 Cross-architecture verification (Apple Silicon/ARM64) found and fixed a new FMA-contraction divergence

A "harsh review" of COMPATIBILITY_REPORT.md flagged a limitation: all measurements had only ever been taken in a single build environment (x86-64 baseline, FMA disabled), and reproducibility on an FMA-enabled target was untested (see COMPATIBILITY_REPORT.md §5). The user actually ran this check on an Apple M5 Mac, and it found **a genuine new bug**.

**Symptom**: building on macOS with Apple clang for ARM64 (Apple Silicon) and running `verify/run_compat.sh --include-slow` FAILed 56 of 178 cases — **every single float-DWT (`-t 0`) case, without exception, both forward and inverse** (integer DWT all PASSed). Worse, for cases like `baseline_256_t0_r0`, even the **encode-side `.bpe` output itself** didn't match, with the `encode .bpe` mismatch starting near the very first bytes (e.g. char 69, char 124) in many cases — an entirely different scale of divergence than §3.3's "rarely off by one pixel," systematic and widespread.

**Root cause**: neither `BPEFLAGS` nor `BPEFLAGS_TRACE` in `original/source/makefile` ever pinned `-ffp-contract`, leaving it up to the compiler's default FP_CONTRACT setting (whether `a*b+c` may be fused into a single-rounding-step FMA instruction). x86-64 baseline targets have no FMA instruction at all, so fusion could never happen there regardless of the default — which is exactly why §3.3's earlier `-ffp-contract=off` experiment (on x86) found no effect: there was no FMA hardware to fuse into in the first place. ARM64 (including Apple Silicon), on the other hand, has FMA as part of its baseline ISA, so the same default setting actually fuses there. Since bpe-rs's `*`/`+` operators on `f32`/`f64` always compute separately and never auto-fuse (a guarantee of Rust's basic arithmetic operators), on a platform where C-side FMA fusion actually occurs, **even the encode side (`forwardf97f`, pure `float` arithmetic, unrelated to §3.3's type-promotion issue)** now diverges from Rust.

**Fix**: added `-ffp-contract=off` to both `BPEFLAGS` and `BPEFLAGS_TRACE`, forcing IEEE754-compliant, per-operator rounding (no FMA fusion) on every target. This makes the C side's floating-point semantics deliberately match Rust's non-fusing semantics everywhere, rather than matching only by hardware-dependent accident.

**Verification results**: confirmed 178/178 PASS on the reporting Mac (Apple M5, ARM64, macOS) after the fix. Also rebuilt and reran the full suite (`run_compat.sh --include-slow`, `run_unit_vectors.py`) on Linux, confirming 178/178 PASS with no regression (as expected, since FMA was never reachable there either way — this was confirmed empirically too, not just assumed).

**Implication**: this discovery closes the loop on a limitation COMPATIBILITY_REPORT.md had flagged about itself (§5, "only verified in one environment") — the user actually verified in a different environment, and it simultaneously proved that limitation's warning was warranted (since a real bug was in fact found). This is a distinct class of risk from §3.3's 1-ULP issue: it's not about type-promotion order, but about "C may implicitly apply an optimization (FMA fusion) that Rust's language semantics never permit" — an independent risk from the promotion-order issue.

## 4. Coverage evaluation (C code exercise rate)

Measured with `gcov` how much of the C reference implementation's actual code the test suite in COMPATIBILITY_REPORT.md §2.1/§2.2 actually exercises (targeting the 15 core algorithm files; `main.c` (CLI argument parsing), the third-party `getopt.c`, and the error-message table `errorhandle.c` are out of scope).

**→ If you just want the current numbers, jump to the three tables below: "Final results," "Reachability breakdown," "Branch reachability breakdown." The other subsections are investigation history (skippable).**

### Correcting the measurement method (a broken `gcov` `.gcda` merge)

Measurements up to this point had **separately recompiled** each shared `.c` file (e.g. `DC_EnDeCoding.c`) with `gcc --coverage -c`, once for the main `bpe` binary (which includes `main.c`) and again for each per-function direct-call generator (e.g. `gen_rice_vectors.c`), before linking. It turned out this approach caused the later-linked side's `--coverage` build to fail to correctly merge the `.gcda` accumulated from the earlier run's execution, silently undercounting the values.

How it was found: adding the 1024-case direct-call generator for `AdjustOutPut` (§3.5) to the existing measurement build, linked in, produced no change whatsoever — not even a fraction of a percent — in `AdjustOutput.c`'s coverage. Running the same generator in an **independent build** that never recompiled the `.c` files it depends on produced 95.70% line coverage for `AdjustOutput.c` alone (matching the baseline value from before §3.6's value diversification) — a result completely different from the existing measurement. This meant not "the generator isn't increasing coverage" but "the measurement method itself was broken."

Fix: changed to compiling every target `.c` file with `gcc -O0 --coverage -c` exactly **once**, and linking both the `bpe` binary and all 6 generators against this shared set of object files (without recompiling) via `gcc --coverage <objs> -o <bin>` (`--coverage` is needed at link time too — for resolving `libgcov` symbols like `__gcov_init`/`__gcov_exit`). Confirmed this approach correctly merges every build's `.gcda` in a single directory. **All figures below are re-measured under this corrected method.** The aggregate figures reported for the 15 core files in past rounds (line 75.96%, branch 66.26%) were undercounts caused by the `.gcda` merge being broken while combining multiple binaries, and are invalidated and superseded by this section's figures. Note that `AdjustOutput.c`'s standalone figures (line 65.02%, branch 56.60%, before §3.5 was applied, measured with the `bpe` binary alone with no merging needed) aren't affected by this merge inconsistency and aren't subject to invalidation — they remain valid as the baseline for §3.5's improvement described later (§4 "Final results").

### Expanding coverage of AC-side functions

`AC_BitPlaneCoding.c` (AC coefficient bitplane coding/decoding) had the lowest line coverage of all files (79.92%/71.88%), so unexecuted lines were identified from `gcov`'s annotated output. The main cause: `ACDepthEncoder`/`ACDepthDecoder` branch on `N` (the bit length of `BitDepthAC_5Bits`), which is derived from the AC coefficients' maximum amplitude, and there's a dedicated 1-bitplane path that bypasses `ACDepthEncoder`/`Decoder` entirely when `BitDepthAC_5Bits==1`. The existing baseline/checkerboard/noise images all landed on either `N==3` or `N==4` (`BitDepthAC_5Bits` 4–15), never hitting the `N==2`, `N==5`, or `BitDepthAC_5Bits==1` branches at all.

Since `BitDepthAC_5Bits` is only known at runtime (dynamically determined from the AC coefficients' maximum amplitude), inputs producing a targeted value had to be searched for **empirically**: a small diagnostic tool was built that reads the header and prints `BitDepthAC_5Bits`, and by repeatedly encoding candidate images and checking the value, it was narrowed down that, for a 64×64 image, "an otherwise near-uniform image with a single +1 offset placed in the very last pixel" gives `BitDepthAC_5Bits==1`, "the same offset placed on an interior pixel" gives `==2`, and "a maximum-amplitude checkerboard (period=1) at 16-bit pixel depth" gives `==17` (`N==5`) — fixed as `ac_depth1_64`/`ac_depth2_64`/`ac_depth5_16bit_64` in `verify/gen_vectors.py`.

Adding these images to `verify/run_compat.sh`, both losslessly (full decode) and in a rate sweep at segment size 16, brought `AC_BitPlaneCoding.c` from 79.92%→86.07% lines and 71.88%→80.73% branches, and `BPEBlockCoding.c` (the block-scan processing AC coding calls) from 93.96%→94.86% lines and 84.20%→85.75% branches. As a side effect, the same segment-size-16 rate sweep also pushed `DC_EnDeCoding.c` (which has the same kind of N-dependent and rate-limit-cutoff branches on the DC side) from 83.04%→88.60% lines and 70.73%→80.08% branches (this wasn't explicitly targeted this time, but since the DC side has a structure paralleling the AC side, the same input set improved both simultaneously).

### Expanding `StagesCodingGaggles.c`'s coverage (segment-size diversification)

Among the 15 core files, `StagesCodingGaggles.c` had the largest absolute number of unexecuted lines (85.93%/81.56%, 82 of 583 lines unexecuted). Reading through it, `StagesDeCodingGaggles1/2/3` decode symbols on the decode side while walking each of stages 1/2/3's quadrant-recursion trees, and there are dozens of branches embedded throughout (right after reading an option, right after reading a value, right after reading a sign bit, etc.) of the form "if the rate limit has just been reached, record the exact position (block number, `X/Y_LocationStopDecoding`) and exit immediately" — this is precisely the code that produces `AdjustOutPut`'s input (where the rate limit stopped).

Most of the unexecuted lines fit this "cut off at exactly this checkpoint" pattern, and which checkpoint actually gets hit depends on where the segment's remaining byte budget runs out. Every sweep up to this point had kept segment size fixed at 64 and varied only the rate, so **varying segment size itself** was an untested dimension. Trying it confirmed that varying segment size reaches new checkpoints far more efficiently than increasing the rate does (since `SEGMENT_S_MIN` in global.h is 16, added 60 cases total: 5 segment-size steps 16–48 × 4 rate steps × 3 images × integer DWT only). float DWT (`-t 0`) was also tried on the same grid; at the time, the same signature as §3.3's 1-ULP residual reproduced at a high rate (11 of 20 combos for noise_256 alone), so it was excluded from this sweep. After §3.3's root cause was later identified and fixed, no mismatches occur on the same grid anymore. However, since `StagesCodingGaggles.c`'s coverage goal is fully achievable with integer DWT alone, the sweep is deliberately kept to integer DWT only.

As a result, `StagesCodingGaggles.c` rose from 85.93%→88.85% lines and 81.56%→83.69% branches. As a side effect, `ricecoding.c` (92.99%→95.15% lines, 88.36%→90.09% branches) and `AdjustOutput.c` (96.93%→97.35% lines, 84.46%→85.16% branches) rose slightly too. The remaining unexecuted lines (65) split between: confirmed dead code from another CLI-unreachable field, `StageStop_2Bits` always fixed at 3 (described later); a defensive branch that's structurally impossible for pattern length to reach 4; harmless no-op debug scaffolding; and the remaining checkpoints (about 54 lines) that still depend on specific timing, of the same nature as `AdjustOutPut`'s remainder.

### Expanding `DC_EnDeCoding.c`'s coverage (N boundaries, negative Max_DC)

While fixing the AC side's N boundary (previous section), it turned out the DC side had the same kind of untouched branch remaining (the DC entropy coder's N==2/N<=4 branches). But the DC side's `N` uses a different formula than the AC side (`N = max(BitDepthDC_5Bits - QuantizationFactorQ, 1)`, where `BitDepthDC_5Bits` itself is a raw value, not a bit-length-of-a-bit-length), so the AC side's "offset a single pixel" technique couldn't be reused, and an empirical re-search was needed.

Investigation with the diagnostic tool found `BitDepthDC_5Bits` tracks the pixel value's magnitude (roughly average pixel value × 8), landing around 12–13 for ordinary natural images. Constructing near-black constant images (values 1, 2) and pairing each with an appropriate lossless/lossy rate confirmed both the `N==2` and `N<=4` branches could be hit (`dc_depth_n2_64`/`dc_depth_n4_64`).

Furthermore, `BitDepthDC_5Bits`'s computation has a separate path (including a correction for the exact-power-of-two case) for when Max_DC is negative in a signed image, and this too was untouched. Combining a signed constant image (a power-of-two negative value, e.g. -128) with an image that's background +20 except a single 8×8 block set to -120 (`dc_negpow_64`/`dc_mixed_sign_64`), all branches of this path were confirmed empirically to be reachable.

As a result, `DC_EnDeCoding.c` rose from 83.04%→93.27% lines and 70.73%→86.18% branches. Almost all of the remaining 23 lines are confirmed dead code (16 lines of `OptDCSelect==FALSE` heuristic branches, 4 lines of defensive `ErrorMsg`); the 2 lines of a specific `QuantizationFactorQ_prime` condition and 1 line of `return k;` that had remained unexplained at the time were settled in a later residual-gap-resolution round (described below) — the former 2 lines were actually covered with a new image, `dc_qprime_lo_64`, and the latter 1 line was confirmed to be confirmed dead code by verifying `DCEntropyDecoder` has no code path that returns anything other than `BPE_OK` (its only error branch calls `ErrorMsg`, which `exit()`s), bringing `DC_EnDeCoding.c` to 100% effective coverage.

### Value diversification for `AdjustOutput.c` (see §3.6 for details)

`AdjustOutput.c`'s coverage plateaued at 97.35% (95 lines unexecuted) with §3.5's structural exhaustiveness (1024 combinations) alone. ### Resolving the residual gap (direct-call harnesses for `StagesCodingGaggles.c`, the AC/DC side, `BPEBlockCoding.c`, and `PatternCoding.c`)

Effective coverage had reached 99.00% (70 lines remaining) by the end of the previous sections, but rather than continuing to pass on those 70 lines as "lower cost/benefit than `AdjustOutPut` since there are fewer of them," the same technique used for `AdjustOutPut` — "link directly against the C reference implementation's object code and drive the function standalone" — was applied, resolving most of them.

**`StagesCodingGaggles.c` (54 lines of stopping-position checkpoints)**: built `verify/c_unit_tests/gen_stages_gaggles_coverage.c`, which calls `StagesDeCodingGaggles1/2/3` directly and exhaustively sweeps `DecodingAllowedBitsSizeInSegment` (a bit-granular budget) from 0 to 150 against a synthesized bitstream built from real files. Since `BitsRead` (bitsIO.c) sets `RateReached` the instant it detects "exactly this bit exceeded the budget," calling the function fresh while varying the budget one bit at a time mechanically reproduces every possible cutoff point right after every read — running a sweep that multiplies the structural combinations of `TypeP`/`TranD`/`TranGi` (3 bits each, 512 combinations total) against DWTType, the custom-weight threshold, and 3 bit patterns newly covered 23 of the 54 lines. Control-flow analysis of the remaining 31 lines proved **all of them confirmed dead code** (details below).

**`DC_EnDeCoding.c`'s `QuantizationFactorQ_prime = BitDepthDC - 3` branch (2 lines)**: the condition `BitDepthDC > 3` and `BitDepthDC - (1+(BitDepthAC>>1)) <= 1` couldn't be hit with images where AC/DC depth tend to move together (both flat images and checkerboards were tried, but the depth difference between the two always stayed fixed at 2, never satisfying the condition). Measuring `BitDepthDC`/`BitDepthAC` empirically across many image patterns with a diagnostic build found that a pattern of **a low, constant background value (2) with a single isolated bump of amplitude 50 in one pixel per 8×8 block** decouples the two (`dc_qprime_lo_64`, `sparse_bump_per_block` in `verify/gen_vectors.py`), newly covering this branch on both encode and decode.

**`PatternCoding.c`'s `RefBitsDe` trailing checkpoint (2 lines)**: `if(BitPlaneStopDecoding!=-1 && RateReached==TRUE){BlockNoStopDecoding=BlockSeq;}`, an end-of-line recording step that, unlike other checkpoints, has no `!LocationFind` guard. Calling directly with `RateReached`/`BitPlaneStopDecoding`/`LocationFind` initialized to mimic "the stopping position was already fixed on a previous bitplane," and the relevant BlockSeq's `RefineBits`-family fields all zeroed (unprocessed), confirmed this line is reached normally and the whole loop passes through — an example of reproducing, via a plain function call, a different kind of state than `AdjustOutPut`'s stopping position: "a later bitplane call continuing within the same segment."

**`AC_BitPlaneCoding.c`'s `RateReached` early return inside `ACGaggleDecoding` (1 line)**: an unguarded, simple `if(RateReached==TRUE)return;`, reached immediately just by sweeping `DecodingAllowedBitsSizeInSegment` in bits from 0 to 40.

These direct-call generators are wired into the coverage-measurement build only, as `verify/c_unit_tests/gen_stages_gaggles_coverage.c`/`gen_residual_gaps_coverage.c` (there's no corresponding verification on the Rust side, and they don't produce output files, so they aren't included in `verify/run_unit_vectors.py`'s exhaustive-verification suite — their purpose is purely measuring the C reference implementation's coverage; C/Rust cross-checking is already covered by the other perspectives).

### Reclassifying reachability: newly proven patterns of confirmed dead code

Thoroughly pursuing the direct-call sweeps above and then running control-flow analysis on the lines that remained to the very end found that **most of the lines classified as "timing-dependent residual gap" were, in fact, deterministically unreachable dead code**. 3 newly found patterns emerged (all variants of the "self-contained redundant guard" pattern found in `AdjustOutput.c`).

1. **The "a narrower checkpoint always intercepts first" pattern** (`StagesCodingGaggles.c`, 30 lines): inside `StagesDeCodingGaggles1/2/3`, only `bitsIO.c`'s `BitsRead` ever sets `RateReached`, and it always updates `BitPlaneStopDecoding` at the same time. Reading through the 3 functions revealed that **every single bit read is immediately followed by a checkpoint dedicated to that specific read** (including the `!LocationFind` guard). That is, the moment `RateReached` newly becomes true, it's always caught by the nearest checkpoint right after it, and once `LocationFind` becomes true, no later checkpoint can ever become true again (same guard condition). So a broader-scope checkpoint — like an unconditional "end of loop" check sitting after one branch of an if/else that involves no read — is structurally unreachable, since a narrower checkpoint always intercepts before it. Forcing the checkpoint condition true externally via `gdb` confirmed control always actually returns at the first (narrower) checkpoint.
2. **The "branch contradicts its entry condition" pattern** (`StagesCodingGaggles.c`, 4 lines): some checkpoints inside `StagesDeCodingGaggles2`/`3` record the coordinate reached only on the `else` side of a 3-way `if(hit_history & 0x4 == 0){...} else if(hit_history & 0x2 == 0){...} else{...}`, but this `else` (both bits already set) is mathematically incompatible with the precondition for entering that checkpoint at all ("there are still 2 or more elements not yet found") — if both bits are set, at most 1 element remains undiscovered, which can't satisfy the entry condition.
3. **The "RateReached and BitPlaneStopDecoding only ever change together" pattern** (`PatternCoding.c`'s `StagesDeCoding`, 4 lines): the only place in the entire source that sets `RateReached=TRUE` is a single spot in `bitsIO.c`, and that same spot always rewrites `BitPlaneStopDecoding` from `-1` at the same time. But some checkpoints inside `StagesDeCoding` judge only `RateReached`, without looking at `BitPlaneStopDecoding` — and this combination (`RateReached==TRUE` and `BitPlaneStopDecoding==-1`) can never arise given the program's overall invariant. Deliberately constructing this contradictory state externally via `gdb` and calling directly did confirm the checkpoint is reached, but this is an artificial state that never occurs in actual decoding — following the standard already established with `AdjustOutput.c` ("respect the program's actual invariants"), it's reasonable to judge this dead code.
4. **The "two consecutive independent conditions' AND is re-checked separately, one side at a time, later" pattern** (`BPEBlockCoding.c`, 2 lines): the `continue` inside `BlockScanEncode` is judged on the AND of 2 conditions, `(A>=BitPlane) && (B>=BitPlane)`, but a bit later there's a branch that `goto`s on `A>=BitPlane` alone, and further along after that, a `continue` on `B>=BitPlane` alone. Reaching both of these latter 2 branches requires both `A>=BitPlane` and `B>=BitPlane` to be true — exactly identical to the first AND condition, which should already have been handled by the first `continue` — a contradiction, so the later `continue` is unreachable.

These proofs brought `StagesCodingGaggles.c`, `DC_EnDeCoding.c`, and `PatternCoding.c` to 100% effective coverage. The single remaining line each in `AC_BitPlaneCoding.c` and `BPEBlockCoding.c` were also proven confirmed dead code via additional control-flow analysis (confirming that `BlockScanEncode`, which `ACBpeEncoding` calls, never calls any output function at all; tracing `BPEBlockCoding.c`'s symbol-slot `si` consumption order — details in each file's description below), bringing all 15 core files to 100% effective coverage.

Of `BPEBlockCoding.c`'s remaining 5.14% (17 lines), 16 turned out to be confirmed dead code. The largest block (13 lines, 357–376) is caused by the loop `for(i=0;i<4;i++) if((TypeC << (1<<(3-i))) != 1) { p=0; break; }`, which judges whether `TypeCi[k]`'s 4 child elements have all been hit — `TypeC` is a 4-bit field (0–15), and once promoted to `int`, at `i=0` (shift amount `1<<3=8`), `TypeC<<8` can only ever be 0 or a multiple of 256, **which can mathematically never equal `1`**. That is, regardless of the actual data, this loop always sets `p=0;break;` on its first iteration (`i=0`), so `p==1` (all hit, the `else` branch that processes only refinement bits) is structurally unreachable — this looks like a typo where `&` should have been written instead of `<<`, but this is how the reference implementation actually behaves, and the Rust side follows suit, preserving compatibility (confirmed by COMPATIBILITY_REPORT.md §2.1's full PASS). Together with the remaining 1 line (`ErrorMsg(BPE_BLOCKSCAN_CODING_ERROR)`, existing defensive code), that's 14 confirmed dead-code lines.

Furthermore, lines 149 and 238 (`continue;`, on a branch involving deep bitplanes with `CustomWtHL1_2bits` etc.), which had been left "unexplained" at the time, were proven confirmed dead code by scrutinizing `BlockScanEncode`'s control flow: these 2 lines sit **a bit after** a `continue` gated on the AND of 2 conditions, `if(A>=BitPlane && B>=BitPlane){continue;}`, with an `A`-only `goto CHECK_GC;` in between, leading to a `B`-only `continue;` (lines 149, 238) further along. Reaching this `B`-only `continue` requires both `A>=BitPlane` (for the `goto`) and `B>=BitPlane` (for the `continue` condition) to be true — exactly identical to the first `A&&B` condition, which should already have been handled by the first `continue` — a contradiction, so the later `continue` is structurally unreachable. This holds true regardless of CustomWt's actual value (fixed anyway, since `CustomWtFlag` is always FALSE) — it's a pure logical redundancy, a variant of the self-contained redundant-guard pattern found in `AdjustOutput.c`.

The remaining 1 line that was originally "unexplained" (line 181, `si++;` — a symbol-index update for when `TranB` has already been found) was also proven confirmed dead code by scrutinizing `si`'s consumption order. This line is reached in either of 2 states: "(A) right after the `TypeP` scan (lines 49–97) records a new hit and increments `si`" or "(B) `TypeP` was already fully discovered and `si` is unchanged" — but the immediately preceding lines 99–100 (`if(SymbolsBlock[si].sym_len!=0)si++;`) have already checked **exactly the same condition** and advanced `si` to the appropriate position: in case (A), it's already advanced to a fresh (`sym_len==0`) slot; in case (B), the slot `si` points to was explicitly reset (`sym_len==0`) by `BitPlaneSymbolReset` on a previous bitplane by `StagesEnCodingGaggles1/2/3`. That is, by the time line 181 is reached, `SymbolsBlock[si].sym_len` is always 0 — the same pattern as `AC_BitPlaneCoding.c`'s `ACBpeEncoding` (below), "the immediately preceding check has already consumed the same condition." This brought `BPEBlockCoding.c` to 100% effective coverage.

### Confirming `header.c`, `bpe_decoder.c`, the AC/DC side, `bitsIO.c`, and `StagesCodingGaggles.c`'s remaining uncovered lines as dead code, error paths, or hard-to-reach cutoff timing

Reading `gcov`'s annotated output directly and checking the surrounding code of the lines that never execute found the following aren't cases testing can't reach — rather, they are **code the C reference implementation itself can never structurally reach from the CLI (or an error path deliberately left out of scope, or a branch that's theoretically reachable but not something a black-box test can realistically target given the timing it depends on)**.

`header.c`:

- `CodewordLength_2Bits` (values 1/2/3, codeword lengths 16/24/32-bit): always hardcoded to `0` by `HeaderInilization`, never changed by any CLI option.
- `CustomWtFlag` (user-defined wavelet weights): likewise always hardcoded to `FALSE`.
- The `UseFill = TRUE` branch: the check `if (SegByteLimit_27Bits == 0) UseFill=FALSE; else UseFill=TRUE;` runs inside `HeaderInilization`, but at this point `SegByteLimit_27Bits` is still its initial value `0`, before being computed from the rate (`-r`) — due to the reference implementation's own initialization ordering, this branch is structurally unreachable.

`bpe_decoder.c` (the remaining 12.13%, confirmed all 33 lines unreachable — no room for improvement with additional testing):

- **The `TransposeImg == TRANSPOSE` branch** (inside `DecodingOutputInteger`/`DecodingOutputFloating`, 18 lines total): the encode side's `HeaderInilization` (header.c:56) always hardcodes `TransposeImg` to `NOTRANSPOSE`, and there's no way to change it to `TRANSPOSE` from any CLI option (`main.c` has no such option). The decode side itself correctly reads it from the header (header.c:308), but this reference implementation's own encoder structurally never writes `TRANSPOSE`.
- **The whole `TempCoeffOutput` function** (9 lines): its only call site inside `DecoderEngine` is already commented out (`//	TempCoeffOutput(...)`) — a debug dump function that's now fully disabled.

### Branch reachability breakdown ("effective branch coverage")

The reachability breakdown so far (the first half of §4) was at the **line** granularity. Since line coverage only sees "was this line executed," a line like `if(coeff > 0) ... else if(coeff < 0) ...` counts as 100% executed as a line even if `coeff`'s sign only ever swings one way — and in fact, this project's DPCM sign bug and `AdjustOutPut` sign bug both manifested in exactly this form: "the line executes, but only one direction of the branch is ever taken." So it's worth evaluating reachability per branch (each direction of a condition), independent of line coverage.

**Method**: among the branch entries `gcov -b` outputs (up to 2 entries per condition expression, taken/not-taken), the unexecuted ones (`taken 0%` or `never executed`) were classified in the following order:

1. **The line itself is already confirmed dead** (already confirmed in the line-level breakdown, first half of §4): if a line never executes, its branch entries are automatically unexecuted too — no new proof needed.
2. **Matches a known dead-code pattern**: CLI-fixed fields like `CustomWtFlag`/`CustomWtH?[HL]?[123]_2bits`, the `N<=5`/`N<=10` family, the `RateReached`/`LocationFind` interception chain, the `TypeC<<(1<<...)` typo, the proof that `BlockScanEncode` never calls `BitsOutput`, the proof that `DCEntropyDecoder` always returns `BPE_OK` — plus the following newly confirmed families this round:
   - **Sign fixed by type**: `diff_AC[i]` is derived from `MappedAC`, which comes from `WORD16` (unsigned), so its sign is structurally fixed (`AC_BitPlaneCoding.c`); `BitMaxAC` is `UCHAR8` (unsigned), so `< 0` is impossible.
   - **A duplicate check of a guard already established on the immediately preceding line**: `bpe_decoder.c`'s `EngImgFlg != TRUE` (already `break`-ed if `EngImgFlg==TRUE` on the preceding line), `bitsIO.c`'s `SegmentFull != TRUE` (already `return`-ed if `SegmentFull==TRUE` just before), `header.c`'s `SegByteLimit_27Bits==0` (already assigned 0 by itself 2 lines earlier).
   - **Error paths (an extension of the existing `fopen(` convention)**: `stat()` failure (`bpe_encoder.c`'s `res != 0`), `ImageSize`/`ImageRead`'s error branches, `fopen` failure (`infile == NULL`) — all applications of the existing "abnormal paths are out of scope" policy, stemming from the tested input file always existing and being readable.
   - **The false direction of the `for(;BlockCounter<TotalBlocks;)` loop condition** (`bpe_encoder.c`): the loop body always exits via `break` when `EngImgFlg==TRUE`, and `EngImgFlg` is constructed to always become TRUE when "the next segment will use up (or overrun) all blocks" — so there's no path where the loop condition itself becomes false and the loop ends naturally — a structural proof that `break` is the only exit.
   - **Encode/decode round-trip consistency**: the `for` loop inside `PatternCoding.c`'s `DeMappingPattern` (the reverse lookup of `bit2_pattern`/`bit3_pattern`/`bit4_pattern_TypeCi`) can never exhaust the table without finding a match and fall out of the loop, given that the encode side's `PatternMapping` wrote the value using this same table. Likewise, `PatternMapping`'s `switch(sym_len)`'s `case 0` and `default` are unreachable, given the structural guarantee that no sym_len==0 symbol is ever generated and sym_len never exceeds 4.
   - **A guarantee that this encoder's own output satisfies the spec**: `header.c`'s `S_20Bits < 16` is unreachable on the side that isn't satisfied, given this encoder is constructed to always compute a spec-conforming value.
   - `BitsPerPixel != 0` (`header.c`) is based on `main.c` initializing it to a default of 1, and this verification's CLI usage never having a test case that explicitly specifies 0 (the same kind of pattern as the other "value fixed by the CLI" family).
3. **`AdjustOutput.c`'s sign guard tautology (486 branches) — [caution: these 486 branches rest on a different, lower rigor level than the other confirmed-dead classifications]**: `AdjustOutPut` has 12 blocks (confirmed via `grep`: pairs for stoppedstage 1/2/3's integer and float representations each, plus 3 pairs equivalent to stoppedstage 4), each with a guard at the top of the loop that excludes 0 in the form `for(m..)for(n..){ if((m==0&&n==0)||(value==0)) continue; ...}`. Since 0 is already excluded by this guard, wherever inside the block a sign branch of the form `if(value>0) ... else if(value<0) ...` sits, the `else if` side, once reached, is always true — "neither 0 nor positive" — so the `else if`'s own false direction (`value>=0` yet still reaching here) is mathematically unreachable. All 12 guard positions were confirmed directly in the source, and this invariant was verified to hold across each one's entire scope, but **not every individual `else if(value<0)` occurrence — which appears 652 times in the text within scope — was re-verified one by one**: this is positioned as a structural confirmation of the mechanism's applicable range, not a claim of the same rigor as the line-level individual proofs. Note that a majority (486) of the 958 confirmed-dead branches rest on this single structural argument.
4. **Implicit defaults where a `switch` statement has mathematically exhausted the value domain (16 branches)**: for something like `switch(BitLength)`, where the source value is limited to a fixed-width bitfield or bitmask's value domain, and every pattern in that domain has an explicit `case`, `gcov` still emits one branch for the implicit "doesn't match any `case`" — since the value domain is mathematically exhausted, this branch is unreachable. Detected structurally (not by text pattern) as "a `switch` line where only the last branch is unexecuted, with 2 or more total branches."
5. **Elimination across a `case`/`if` chain (domain elimination, newly added)**: `CodingOptions`'s `sym_len==4` (sym_len's domain is only {1,2,3,4}, 1 is already `continue`d, and 2 and 3 are already ruled out by the immediately preceding `if`/`else if`); `StagesEnCodingGaggles1`'s `sym_len==3` (the domain is limited to {1,2,3} by the outer `switch(sym_len){case 1:2:3:}`, then further eliminated); `StagesEnCodingGaggles2/3`'s `sym_len==4` (the `else` side is `ErrorMsg`, confirmed unexecuted via gcov's execution count `#####` — for this `type` set, only 2/3/4 are valid values for `sym_len`). `PatternMapping`/`DeMappingPattern`'s `case 4` (a 4th implicit branch for when `type` is none of `TYPE_CI`/`TRAN_HI`/`TYPE_HIJ` — sym_len==4 symbols are only ever generated for these 3 `type` values).
6. **Structural proof of a tie-breaking chain via transitivity (newly added)**: for `CodingOptions`'s Rice-split option selection (the `<=` chains for `bitsCounter_3Bits`/`bitsCounter_4Bits`), some of the later `else if` clauses were individually proven to be mathematically forced by the very fact that the earlier clauses failed. For example, 3-bit's 2nd clause `(c0<=c1)&&(c0<=c2)`'s `c0<=c2` side: once the 1st clause `(c2<=c0)&&(c2<=c1)` fails (whether because `c2>c0` or `c2>c1`), combining that with `c0<=c1` always forces `c0<=c2` — any attempted counterexample runs into a contradiction. The same kind of transitivity was confirmed for 3-bit's 3rd clause (the `c1<=c2` side) and 4-bit's 2nd clause (the `c0<=c3` side).
7. **`RefBitsDe`'s cutoff-position recorder (newly added)**: the remaining 2 spots involving `!PtrCoding->DecodingStopLocations.LocationFind` — this check is only ever reached when "`RateReached` transitioned from false to true *during this call*" (having passed the early `return` on `SegmentFull||RateReached` at the top of the range means it must have been false at the start of the call). `LocationFind` can only already be true from some *other*, earlier call — but that call must also have made `RateReached` true, which would then hit that same early-`return` guard on the *next* call and end the function before reaching this depth. That is, "reaching here while `LocationFind` is already true" is structurally impossible.
8. **The remaining 5 branches of the 4-bit Rice-split option selection → all resolved (1 case reached via an added test, 4 proven structurally unreachable)**: for `CodingOptions`'s 4-bit-side `else if` chain (judging in order whether `bitsCounter_4Bits[0..3]` is the minimum, lines 316/322/328/334, corresponding to Option 3/0/1/2 respectively), 5 branches at lines 328, 330, 334, 335, 336 had long remained unresolved — "no counterexample could be deliberately constructed from real data, and no mathematical proof of unreachability existed either." Digging further into this `else if` chain's structure resolved all of them, as follows.
   - **Line 328 (the false direction of `bitsCounter_4Bits[1] <= bitsCounter_4Bits[0]`): turned out reachable, resolved by adding a test**. Mixing 4 instances of TYPE_CI's pattern value 0 and 3 of pattern value 6 (via `bit4_pattern_TypeCi`'s reverse lookup, `sym_val` = 8×4, 3×3) yields `bitsCounter_4Bits` = `(25,26,24,28)` — line 316 (`c3` minimal) and line 322 (`c0` minimal) both fail, yet `c1(26) > c0(25)`, making line 328's first condition false — a direction no existing case had produced. Added this case to `verify/c_unit_tests/gen_codingoptions_coverage.c`, and confirmed empirically (via `gcov -b`, a standalone direct-call build of `PatternCoding.c`) that line 328's false direction flipped from 0% to executed.
   - **Line 330 (the false direction of `bitsCounter_4Bits[1] <= bitsCounter_4Bits[3]`): proven structurally unreachable**. Assuming lines 328–329 are true (`c1` is at or below `c0` and `c2`) while line 330 is false (`c1 > c3`) derives, by transitivity, `c3 < c1 <= c0` and `c3 < c1 <= c2`; combined with `c3 <= c1` (trivially true from the assumption), all 3 of line 316's conditions (`c3<=c1 && c3<=c0 && c3<=c2`) end up satisfied — but line 316 is evaluated before line 328, so by the time control reaches line 328, line 316 must already be false. Contradiction. So the state "lines 328–329 true and line 330 false" can never arise.
   - **Lines 334, 335, 336 (all 3 conditions judging whether `bitsCounter_4Bits[2]` is minimal): proven structurally unreachable**. For any 4 real numbers, "at least one of them is at or below the other 3" (i.e. is a minimum, possibly tied) is a tautology — once lines 316, 322, 328's conditions (whether `c3`/`c0`/`c1` is a minimum candidate, respectively) are all false and control reaches line 334's judgment, the remaining 4th option of this 4-way exhaustion, "`c2` is a minimum candidate" (line 334-336's entire conjunction), is automatically guaranteed true. Since the conjunction is true, each of lines 334, 335, 336's individual conditions must also be true — so this trio's false direction (the `taken 0%` side) can never occur for any input.

- **`StagesCodingGaggles.c`'s bitplane-significance history (5→0)**: the remaining 2 branches of `TranD&0x2==0`/`TranGi&0x2==0` were resolved via a transitivity proof showing the preconditions for reaching them (`counter>=2`, and a higher bit already set by the preceding `if`) force the value into exactly 1 possibility. The remaining 3 (the `sym_len==3`/`==4` branches) were resolved with a new direct-call generator for `StagesEnCodingGaggles1/2/3` (`gen_stages_encode_coverage.c`), after fixing a case that initially crashed on `ErrorMsg` from not realizing `TYPE_P` symbols only go up to length 3 (only `case 1:2:3`, no `case 4`).

**Lessons learned in the process (recorded for future investigations of the same kind)**: (a) `gcov`'s branch label `branch N taken X% (fallthrough)`, on a line with a chain of `if`/`else if`s, refers to "that line's condition being true and falling through to the code right after it" (i.e. the `if` side is the `fallthrough`, not the `else` side) — this was mistaken at one point, leading to added tests written in the wrong direction that had to be redone. It's recommended to always corroborate with execution counts (`gcov -c`'s raw counts, or matching against the corresponding body line's execution count). (b) Repeatedly recompiling and relinking the same `.o` file with different content can corrupt the accumulated coverage data for the affected file via a `.gcda` checksum mismatch (this actually happened this round, recovered by rebuilding and re-running every harness from object generation, once, straight through) — when continuing measurement across multiple rounds, avoid partial rebuilds along the way, and always do the final confirmation with one clean, complete measurement run.
