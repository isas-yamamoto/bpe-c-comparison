# C/Rust Compatibility Verification Report

[日本語版](COMPATIBILITY_REPORT.ja.md)

This report summarizes, for the compatibility between `original/` (the C reference implementation of CCSDS 122.0 Bit Plane Encoder, bug-fixed version by Aaron Kiely) and `bpe-rs/` (its Rust port), what perspectives were used, how it was tested, and what was found. The test harness lives in `verify/`; how to run it is documented in [README.md](README.md).

Commits as of writing: this repository ([bpe-c-comparison](https://github.com/isas-yamamoto/bpe-c-comparison)) from `ee40b71` onward / [bpe-rs](https://github.com/isas-yamamoto/bpe-rs) `8ae7bbf`.

**Scope definition**: the "compatibility" this report verifies is byte compatibility with this specific C reference implementation's (`original/source/`, the bug-fixed version by Aaron Kiely) actual behavior — not conformance to the CCSDS 122.0 spec itself. Quirks and apparent typos in the reference implementation's own code (e.g. `TypeC<<(1<<(3-i))`, covered in [INVESTIGATION_LOG.md](INVESTIGATION_LOG.md) §4) are likewise not treated as things to verify against the spec and fix, but as targets for "does the Rust side reproduce the same behavior" — a deliberate choice, given the goal is to replace the reference implementation.

**File structure**: this file is the current-state reference (§0, §1, §2, §5, §6 below plus "Reproduction steps") — overwritten in place as the project's state changes, and kept reasonably short. The chronological investigation log behind these conclusions — every bug hunt, coverage round, and open item, in the order they happened — lives in the companion file **[INVESTIGATION_LOG.md](INVESTIGATION_LOG.md)**, as §3, §4, and §7 (section numbers are kept identical to when both lived in one file, so all the existing "(§3.3)"-style citations throughout both files still point at the right place — they just now mean "look in INVESTIGATION_LOG.md" instead of "look further down this same page"). That file only ever grows; this one gets rewritten.

## 1. Verification perspectives

Since "compatible" can't be measured by a single metric, five perspectives of a different nature are combined.

| # | Perspective | What it verifies | Why it's needed |
|---|------|----------------|-----------|
| 1 | Full-pipeline byte compatibility | Encode/decode real images with both implementations and check whether the output byte streams match exactly | This is ultimately the only thing users care about. But to avoid conflating "happened to match on today's test images" with "always matches," images deliberately targeting known boundary values are mixed in |
| 2 | Coverage of known edge cases | Prepare inputs that reproduce the real bug fixes Aaron Kiely recorded in `original/readme_kielymods.rtf` (single-block segments, all-zero images, block-count boundaries, endianness, etc.) and check whether they match there too | Ordinary natural images rarely hit the boundary values that tend to breed bugs. Without deliberately constructing edge cases, "it matched" doesn't mean much |
| 3 | Exhaustive function-level verification | Cross-check Rice coding, two's-complement conversion, DPCM DC mapping, pattern mapping, and `CodingOptions` across the entire (or near-entire) representable input domain, using generators linked directly against the C reference implementation's object code | Perspectives 1 and 2 only exercise "the values that image happens to generate." They can't cover the full range of values an individual function can receive. In fact, the DPCM bug described later was never hit by any ordinary test image |
| 4 | Randomized fuzz testing | Randomly combine image size, bit depth, signedness, byte order, rate, segment size, and pixel content, and repeat the same byte-compatibility check as perspective 1 at scale (`verify/fuzz_compat.py`) | Perspectives 1 and 2 only exercise hand-picked combinations. "100% coverage" only means a branch was executed at least once — it can't rule out a mismatch on a different value that takes the same branch. This perspective compensates for that |
| 5 | Stage-boundary trace comparison | Dump and diff intermediate values from both implementations right after the DWT transform and right after block-string construction (`verify/compare_traces.py`) | A diagnostic tool for immediately pinpointing "at which stage of the encoder did the two diverge" when perspective 1 finds a mismatch. It is not itself a pass/fail criterion |

In addition to the above, **code coverage measurement** (INVESTIGATION_LOG.md §4) quantifies how much of the C code perspectives 1 and 2 actually exercise, making visible the "still-unverified areas" that these perspectives alone can't reveal.

## 2. Test contents and results

### 2.1 Full-pipeline byte compatibility (`verify/run_compat.sh`)

166 cases (one of which is a low-frequency regression case that only runs with `--include-slow`). All cases confirmed **encode output byte match, and cross-decode output byte match (C→Rust and Rust→C, both directions)**.

**Result: 166/166 PASS** (as of 2026-07-26; the first run FAILed 12 cases when the decode-side byte-order-inversion cases were added — see INVESTIGATION_LOG.md §3.7).

### 2.2 Exhaustive function-level verification (`verify/run_unit_vectors.py`)

| Target function | C reference implementation | Coverage | Verification method |
|---|---|---|---|

C's generated byte stream is also fed to the Rust decode to confirm it correctly recovers the original value sequence (cross-decode) |
| `ConvTwosComp` | DC_EnDeCoding.c | leftmost = 2–16 × the entire representable value range for each width | Rust's `conv_twos_comp` output matches C exactly |

| `DPCM_ACMapper`/`DPCM_ACDeMapper` | AC_BitPlaneCoding.c | N = 2, 3, 4, 5 (the full range `ac_depth_encoder` supports) × the same 3 series | Rust's `dpcm_ac_mapper`/`dpcm_ac_demapper` output matches C exactly (no mismatches, see INVESTIGATION_LOG.md §3.4) |

| `ACDepthEncoder`/`ACDepthDecoder` | AC_BitPlaneCoding.c | BitDepthAC_5Bits values representative of the entire N(2-5) range `ACDepthEncoder` supports × 5 segment sizes (roughly 1–3 gaggles' worth) × 3 BitMaxAC distribution patterns (ramp/extremes/mid-boundary) = 120 combinations | Rust's `ac_depth_encoder` output byte stream matches C exactly. | `DCEntropyEncoder`/`DCEntropyDecoder` | DC_EnDeCoding.c | All reachable patterns among `QuantizationFactorQ_prime`'s 4 branches for N≥2 × 4 N-brackets (2/≤4/≤8/>8) × 5 segment sizes × 3 ShiftedDC distribution patterns = 75 combinations (§4.3.3's extra bitplane, present or absent, both included) | Rust's `dc_entropy_encoder` output byte stream matches C exactly. **Result: 9/9 test groups PASS** (though, as described below, the DC-side DPCM only reached PASS after finding and fixing 2 mismatches on the first pass).

While generating test vectors for `ACDepthEncoder`/`DCEntropyEncoder`, it turned out `CustomWtLL3_2bits` (the LL3 subband's default weight value) was mistakenly zero-initialized — `HeaderInilization` always hardcodes it to `3` (a separate matter from `CustomWtFlag` always being FALSE; this one is never 0), and `DCEntropyEncoder` uses this value via `max()` in both its `QuantizationFactorQ` and `numaddbitplanes` computations. After fixing the generator to use this value, it was confirmed that bpe-rs's own implementation (`dc_entropy_encoder` itself, in `dc/entropy.rs`) had folded in `custom_wt_ll3` correctly from the start — a test-harness initialization gap, not an implementation bug.

### 2.3 Randomized fuzz testing (`verify/fuzz_compat.py`)

§2.1's 166 cases are a hand-built matrix targeting known edge cases, so input combinations outside it remain, in principle, unverified. To compensate, a fuzz harness was added that randomly combines image size, bit depth, signedness, byte order, rate, segment size, and pixel-content pattern, and repeats the same encode-match plus cross-decode-match check as §2.1 at scale. It targets both integer and float DWT (default `--dwt-type both`). The earlier version excluded float DWT as noise from INVESTIGATION_LOG.md §3.3's "known 1-ULP residual," but now that the root cause has been fixed, float DWT is just as meaningful a target as anything else, with no reason to exclude it. Rate/segment-size combinations the encoder structurally can't accept (`BPE_RATE_ERROR`, an input-validity issue rather than a C/Rust difference) are handled by automatically retrying at a higher rate.

Integrated into CI in two tiers: a lightweight smoke test of 50 fixed-seed cases on every push/PR, and a deep fuzz of 5000 random-seed cases (the `deep-fuzz` job) on a weekly schedule/manual dispatch. Locally, 500 cases (`--seed 123`) and 3000 cases (`--seed 999`) have been run across both DWT types with 0 mismatches confirmed.

### 2.4 Stage-boundary trace comparison (`verify/compare_traces.py`)

Set up a mechanism to diff 5 points beyond the encode side (right after the DWT transform, right after block-string construction): on the decode side, `adjust_output`'s output, right after segment reassembly, right after the inverse-DWT levels 2/1 complete (level-granularity boundaries `post_idwt_level2`/`post_idwt_level1`), and right after the inverse DWT. Integer DWT matches at every stage. Float DWT now also matches at every stage after INVESTIGATION_LOG.md §3.3's root-cause fix. This level-granularity breakdown was set up precisely in the process of identifying which level that 1-ULP difference occurred at (`inverse_lifting97f`'s levels) — it's less a standing pass/fail gate than a primary triage tool for the next time a similar mismatch shows up.

## 5. Overall assessment

- **For the ordinary encode/decode path (no rate limiting, or mild lossy compression), compatibility has been confirmed with high confidence.** Both the byte-compatibility and exhaustive function-verification tests PASS, and integer DWT shows 0 mismatches across the range tested.
- **Both function-level verification and the rate sweep independently found real bugs**: the 2 DC-side DPCM bugs were found via §2.2 (function level), and the inverse-DWT precision mismatch via §2.1's rate sweep. The premise that "the byte-compatibility test passing" doesn't mean "matches under every input and condition" was independently corroborated by 2 methods of a different nature.
- **The 1-ULP-level residual that used to exist in float DWT decoding has been root-caused and fully fixed** (INVESTIGATION_LOG.md §3.3). It was originally misdiagnosed as "an unresolvable residual difference due to a compiler difference between gcc and rustc," but it was actually a fixable implementation bug: bpe-rs's `inverse_lifting97f` failed to reproduce C's per-operator type-conversion rules (add in f32, then promote to f64). After the fix, 0 mismatches across both integer and float DWT (178/178 cases, 3500 fuzz-test cases).
- **Rate-limited mid-decode recovery (`AdjustOutPut`) broke past the full-pipeline test's limits via direct function calls, rising from 65.02%→96.90% lines** (INVESTIGATION_LOG.md §3.5, §4). The in-block stopping coordinates (`X`/`Y_LocationStopDecoding`, 64 combinations of 8×8) were almost entirely unreachable from the full-pipeline test, due to depending on the bitstream's remainder — switching to the technique of linking directly against the C reference implementation's object code and driving the function standalone (already proven with Rice/DPCM/pattern mapping) made it possible to directly exhaust all 1024 combinations of DWTType × stoppedstage × DC branch × X/Y coordinate, with 0 mismatches.
- **`AdjustOutPut`'s remaining 95 lines (found to be caused by a lack of value-sign variation) were pushed to 97.35%→99.55% lines by adding a sign-inversion/phase-shift `variant` dimension to the test values, expanding to 6144 combinations, and the last 16 lines were proven confirmed dead code (a redundant guard's `else` clause) via control-flow analysis** (INVESTIGATION_LOG.md §3.6, §4). `AdjustOutPut.c` ultimately reached 100% effective coverage (fully exhausted once dead code is excluded), and since this single function alone accounts for about 49% of the entire core algorithm's line count, it was a major factor pushing up the 15 core files' overall effective coverage (ultimately 100.00%, INVESTIGATION_LOG.md §4).
- **The 15 core files' overall line coverage reached 95.14% (86.79% branches), well above the originally targeted 90%.** This is the cumulative result of `AdjustOutPut`'s direct-call harness and value diversification, plus the direct-call harnesses for `StagesCodingGaggles.c`, the AC/DC side, and `PatternCoding.c` (described in INVESTIGATION_LOG.md §4) — the remaining gap sits at a near-ceiling level of just 1 line each in `AC_BitPlaneCoding.c` and `BPEBlockCoding.c`.
- **All 5 remaining branches in `PatternCoding.c`'s 4-bit Rice-split option-selection chain have been resolved (INVESTIGATION_LOG.md §4 "Branch reachability breakdown" item 8).** 1 branch (line 328's false direction) was resolved by newly discovering a concrete counterexample symbol-value combination and adding it as a test; the remaining 4 (lines 330, 334, 335, 336) were proven structurally unreachable via the tautology "of 4 real numbers, one is always at or below the other 3" plus transitivity. This brought all 15 core files to 100.00% effective coverage (both line and branch), leaving no "unproven" item remaining in this report.
- **Excluding confirmed dead code (356 lines, 4.9% of the total), "reachable code"-based effective coverage reaches 100.00%** (INVESTIGATION_LOG.md §4's reachability breakdown table). The raw figure of 95.14% alone can't tell you whether "the rest can still be filled in with more testing effort, or genuinely can't be" — so unexecuted lines were manually classified, file by file, into "confirmed dead code/error path" versus "reachable residual gap." Originally about 1.0% (70 lines) of genuine headroom remained, but applying the same "direct call + exhaustive sweep" technique used for `AdjustOutPut` to `StagesCodingGaggles.c`, the AC/DC side, and `PatternCoding.c` resolved almost all of it (actually covering it) or proved it confirmed dead code (verified via externally forcing state with `gdb`) — with the final 1 remaining line each in `AC_BitPlaneCoding.c` and `BPEBlockCoding.c` also proven confirmed dead code via control-flow analysis (confirming the former's callee never has any output function at all; tracing the latter's symbol-slot consumption order) — bringing the genuinely unexplained residual gap across all 15 core files to **zero**.
- **`StagesCodingGaggles.c` (the code that records the rate-limited decode's stopping position), following the segment-size-varying sweep (a previous round, 85.93%→88.85% lines), rose further to 88.85%→92.80% lines and 83.69%→87.06% branches by newly building a harness that directly calls and exhaustively sweeps the bit budget of `StagesDeCodingGaggles1/2/3`** (INVESTIGATION_LOG.md §4). The remaining 42 lines were all proven confirmed dead code via 2 patterns — the structural redundancy where a narrower checkpoint always intercepts first, or a coordinate-selection `else` branch that mathematically contradicts its own entry condition — reaching 100% effective coverage.
- **Discovered and fixed a measurement bug in the coverage-measurement method itself: a `gcov` `.gcda` merge inconsistency** (INVESTIGATION_LOG.md §4). Because shared `.c` files were being recompiled per binary, a later link failed to correctly merge the earlier run's `.gcda`, and every figure reported in past rounds (e.g. 75.96% lines across the 15 core files) was an undercount. Changed to compiling every target file exactly once and reusing the shared objects across all binaries; this report's figures are the corrected measurement.
- **`bpe_decoder.c` rose from 66.18%→87.87% lines and 50.00%→79.17% branches by exhaustively expanding the combinations of pixel format, DWTType, and byte order** (INVESTIGATION_LOG.md §4). In particular, an added case targeting the point that "decode-time byte order is an independent CLI setting, unrelated to the value used at encode time" led directly to discovering a real Rust bug (INVESTIGATION_LOG.md §3.7). The remaining ~12% is the `TransposeImg` branch, a disabled dump function, the `UseFill`-gated fill skip-over loop, and error paths — all confirmed unreachable code or out of this report's scope (see INVESTIGATION_LOG.md §4).
- **`bpe_encoder.c` had already grown substantially (+8-9 points, a previous round) by increasing pixel-format diversity (signed, non-default bit depths).** Reading `gcov`'s annotations directly to identify unexecuted lines, and targeting only the ones reachable from the CLI, proved effective.
- **`header.c`'s remaining ~22% (~44% of branches) was determined to be dead code that testing can't fill in.** There's no point adding further test cases to this file.
- **Added function-level verification for AC-side DPCM and confirmed no bug** (INVESTIGATION_LOG.md §3.4). The same concern raised on the DC side has been resolved.
- **The AC side's remaining major functions (`ACGaggleEncoding`/`ACGaggleDecoding`/`ACDepthEncoder`/`ACDepthDecoder`) rose from 79.92%→86.07% lines and 71.88%→80.73% branches with 3 images constructed to target AC coefficient amplitude (`BitDepthAC_5Bits`), then further to 86.48% lines and 82.81% branches with a direct-call sweep of `ACGaggleDecoding`** (INVESTIGATION_LOG.md §4). `BPEBlockCoding.c` also rose slightly as a side effect. The remaining gap is the heuristic branch unreachable because `OptDCSelect`/`OptACSelect` are always TRUE (the same kind as `header.c`'s dead code), and the defensive `ErrorMsg` for `N>5` (mathematically unreachable) — the last line inside `ACBpeEncoding` (the `SegmentFull` early return right after a `BlockScanEncode` call) was also proven mathematically equivalent to the identical check right before it, since `BlockScanEncode` never calls any output function, bringing `AC_BitPlaneCoding.c` to 100% effective coverage.
- **The DC side (`DC_EnDeCoding.c`) likewise rose from 83.04%→93.27% lines and 70.73%→86.18% branches with 4 images targeting the same kind of N-boundary and negative-Max_DC issues, then further to 93.86% lines and 87.80% branches with the `dc_qprime_lo_64` (low background + isolated bump) image and analysis of `DCEntropyDecoder`'s return value, reaching 100% effective coverage** (INVESTIGATION_LOG.md §4). Unlike the AC side, the DC side's `N` has no bit-width mathematical upper bound, but `QuantizationFactorQ_prime`'s selection formula is designed to always keep `N` at or below 10, confirming the defensive `ErrorMsg` for `N>10` is structurally unreachable.
- **`bitsIO.c` (the remaining 19 lines) was, after further investigation, confirmed entirely and deterministically unreachable, with no further gains possible from additional test cases** (INVESTIGATION_LOG.md §4). The `CodeWord_Length` 16/24/32-bit branches share the same cause as the known dead code from `CodewordLength_2Bits` always being 0. The `RateReached==TRUE` early return was confirmed, via a full source grep, to always be set and reset simultaneously with `SegmentFull`, and the preceding `SegmentFull` check always returns first. The `length>32` branch was judged practically unreachable based on the empirical coefficient range implied by the reference implementation's 16-bit pixel-depth ceiling (max `BitDepthDC_5Bits` observed was 19). The segment-trailing fill skip-over loop (2 lines) was actually covered as a side effect of adding the `dc_qprime_lo_64` test.
- **The very act of raising coverage became the trigger for discovering a real, previously hidden Rust bug (the decode-side ignoring of `-f`, INVESTIGATION_LOG.md §3.7).** This shows that filling in code-coverage gaps isn't merely improving a number — it's also a substantive verification act that exposes oversights in the test matrix itself (patterns that had been hiding a Rust-side bug).
- **Overall, "compatibility has been proven" can only be said for the test scope described in this report** — it isn't a state where "fully compatible for all inputs" has been mathematically proven unconditionally (see INVESTIGATION_LOG.md §7 item 13). That said, known differences currently stand at **zero** (float DWT's 1-ULP residual has also been fixed, in this section). Future test expansion (especially the still-untouched AC-side functions) is designed to further widen the scope of this guarantee (each script under `verify/` can be extended following the same pattern).
- **Most measurements in this report were taken in a single build environment** (one gcc version, one rustc version, the x86-64 baseline target, FMA disabled), **but one cross-architecture check was actually run — on an Apple M5 (ARM64/macOS, Apple clang) — and it found and fixed a real new bug** (INVESTIGATION_LOG.md §3.10). On ARM64, where FMA is part of the baseline ISA, the C compiler's default FP_CONTRACT setting fused both forward and inverse float-DWT arithmetic into FMA instructions, diverging widely from Rust (which never auto-fuses) — fixed by pinning `-ffp-contract=off` in the Makefile. This one case both vindicates the earlier warning that only one environment had been tested, and shows that gap has now actually been closed. That said, reproducibility on a different gcc/rustc version, other ARM implementations besides Apple Silicon, and other optimization levels (`-O0`/`-O3`, etc.) remain **untested**. Noted here as a known limitation.

## 6. Cross-checking against external reference documents

Cross-checked, item by item, the issues raised against the C reference implementation in [oresat/libbpe's `UNL_readme_kielymods.txt`](https://github.com/oresat/libbpe/blob/master/bpe/source/UNL_readme_kielymods.txt) (accessed 2026-07-25) against the current code in `original/source/*.c`. This document is **word-for-word identical** to this repository's `original/readme_kielymods.rtf` (Aaron Kiely, June–July 2008), and `original/source/*.c` was brought into this repository as a version that already has this document's fixes applied in the first place. Results after actually reading the code to confirm:

| # | Issue raised | Location | Verdict |
|---|---|---|---|
| 1 | With `gaggles==0` (the final segment of a single block), `ACGaggleEncoding`/`ACGaggleDecoding`/`DCGaggleDecoding`/`DCEncoder` exit without doing anything | AC_BitPlaneCoding.c, DC_EnDeCoding.c | **Fixed**. All 4 functions consistently use `gaggles` as a "count of values" via `for (i = StartIndex; i < StartIndex + gaggles; i++)`; there's no early return for `gaggles==0` |
| 2a | `DCEntropyEncoder` codes `q - WtLL3` DC extra bitplanes per section 4.3.3 (too many) | DC_EnDeCoding.c:239-243 | **Fixed**. Computes `q - max(BitDepthAC, WtLL3)` |
| 2b | `DCDeCoding`'s section-4.3.3 bit-decoding logic remains commented out | DC_EnDeCoding.c:693-714 | **Fixed**. Present as active code (explicitly marked `/* --- Begin/End bug fix (Kiely) --- */`) |

| 3 | Inside `AdjustOutPut`, the `DeConvTwosComp` call for `ShiftedDC + DecodingDCRemainder` lacks a `(long int)` cast, which can overflow | AdjustOutput.c:50-57 | **Fixed**. Both operands have a `(long int)` cast. The buggy version remains only as a comment |
| 4 | `DCGaggleDecoding`/`ACGaggleDecoding`'s loop variable `i` is `short`, overflowing at 2^15 or more blocks/segments | DC_EnDeCoding.c:262, AC_BitPlaneCoding.c:295 | **Fixed**. Both are `long int i` |
| 5 | A bug in the DPCM mapping's sign-inversion formula and `DPCM_DCDeMapper`'s branch structure | DC_EnDeCoding.c (DPCM_DCMapper/DeMapper) | **Fixed**. Both the `-(short)( ((X^Bits1)&Bits1)+1 )` form and the `if (MappedDC > 2*theta) { if ((long int)ShiftedDC[i-1] < 0) ... }` form are applied. The buggy version remains only as a comment |

This cross-check produced no additional code changes to `original/source/*.c`, so all test results and coverage evaluation across this report and INVESTIGATION_LOG.md remain fully valid as-is.
